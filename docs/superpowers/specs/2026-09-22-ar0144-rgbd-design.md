# AR0144 Stereo → Depth → RGBD, for RTAB-Map SLAM

Date: 2026-09-22
Status: draft, awaiting review
Hardware: Waveshare AR0144 Stereo USB Camera (A)

## 1. Purpose and scope

Turn the AR0144 stereo module into a calibrated metric depth source, and expose
it as:

1. a Python API returning aligned `(rgb, depth, K)` frames,
2. a live viewer and an on-disk recorder,
3. calibration in the format RTAB-Map consumes, so the camera can drive SLAM.

Consumers are **RTAB-Map standalone** for SLAM and a **debug visual RGBD
output** for inspecting depth quality. Confirmed: no ROS 2 anywhere.

**Out of scope**: a ROS 2 node (dropped outright, not deferred), IMU fusion,
learned stereo matchers, GPU acceleration. Section 12 records the rest.

## 2. Hardware characterisation (measured, not from the datasheet)

All of the following was measured on the device, because the bundled PDF is a
generic 2018 USB-camera manual and the vendor wiki is behind Cloudflare.

The module is **one UVC node** (`CCB Camera`, USB `26e0:ccb1`) that emits a
single horizontally-concatenated frame `[ left | right ]`. Both eyes are
therefore captured and delivered as one buffer, so they are hardware
frame-synchronised with no software pairing and no possibility of drift. Both
sensors are **colour**, global shutter.

### 2.1 Modes

| Requested | Per eye | Relationship to sensor | f (px) | HFOV | VFOV | fps |
|---|---|---|---|---|---|---|
| 2560×720 | 1280×720 | reference | 1004 | 65.0° | 39.4° | 30 |
| 1600×600 | 800×600 | crop 960×720, then scale | 837 | 51.1° | 39.4° | 30 |
| 1280×480 | 640×480 | crop 960×720, then scale | 670 | 51.1° | 39.4° | 60 |
| 1280×360 | 640×360 | pure 2× downscale | 502 | 65.0° | 39.4° | 120 |
| 1280×720 etc. | — | **left sensor only**, not stereo | | | | |

Two facts here are easy to get wrong and both cost real accuracy:

- **The 4:3 modes are a horizontal crop, not a downscale.** They discard 25% of
  the horizontal field of view. Established by upscale-and-template-match
  against the 1280×720 reference eye (correlation 0.997): the 800×600 and
  640×480 modes cover 960 of 1280 reference columns and the full 720 rows,
  while 640×360 covers all 1280×720.
- **Requesting a single-width size silently yields one eye.** The driver does
  not error; it hands back a 1280-wide frame. Splitting that in half produces
  two halves of the left image that look plausibly like a stereo pair. Every
  capture path must assert the returned width.

`f` above is derived from the 65° horizontal FOV spec at the reference width and
scaled by the crop/scale factor. These are priors for sanity-checking
calibration, **not** substitutes for it.

### 2.2 Formats

`MJPG` and `YUYV`. On USB 2.0, MJPG is mandatory: 2560×720 YUYV is capped at
5 fps by bus bandwidth (2560·720·2 B · 30 = 110 MB/s). FOURCC must be set
*before* the frame size or the V4L2 backend ignores it.

### 2.3 Photometric consistency between the eyes

The device exposes **one** UVC control set (exposure, gain, white balance) for
both sensors. An earlier draft of this spec concluded from that the two eyes
are photometrically identical, "which is what stereo matching wants". **That
was wrong**, and the correction matters because SGBM's cost function assumes
the eyes agree.

Measured on a centre patch, right eye versus left, as R/G ratio (ratios cancel
overall brightness, isolating colour):

| Control state | R/G difference | B/G difference |
|---|---|---|
| Auto exposure + auto WB (factory) | −7.6% | +2.1% |
| Auto exposure + auto WB, second capture | −5.8% | −0.5% |
| **Manual exposure, WB fixed at 4600 K** | **+21.7%** | **−17.3%** |

Two conclusions:

- **The eyes are not photometrically identical**, even under full auto: a
  residual ~6% colour difference and a few percent brightness difference
  persist. One control set does not mean one result.
- **Disabling auto white balance makes it far worse** — a −6% difference
  becomes +22%. The auto path evidently compensates per-eye; a fixed white
  point exposes the sensors' differing spectral response.

This creates a genuine conflict:

| | Auto AE/AWB | Locked AE/AWB |
|---|---|---|
| Inter-eye consistency (stereo matching) | better (~6%) | worse (~22%) |
| Temporal consistency (VO tracking, loop closure) | poor — drifts per frame | good |

SLAM needs locked exposure: auto-exposure changing between frames breaks
feature tracking and RTAB-Map's appearance-based loop closure. So the design
**locks exposure and gain and compensates the inter-eye difference explicitly**
rather than leaning on AWB to hide it:

1. **Match on grayscale with per-eye normalisation** (equalise mean and
   variance over the overlapping region) before SGBM. This removes gain and
   colour mismatch in one step and costs almost nothing.
2. **Measure per-eye colour gains during calibration** against a neutral
   target, store them in `calibration.json`, and apply them to the RGB output.
3. Choose and record the white-balance setting at calibration time, so the
   stored gains and the runtime white point agree.

Caveat on the numbers: the two eyes view slightly different scenes and have
their own vignetting, so part of the measured difference is scene content. The
large AWB-off effect is unambiguous; the residual ~6% needs a uniform neutral
target to pin down, which is why item 2 belongs in the calibration phase.

**Operational note:** UVC control values live on the device and persist after a
process exits, so a tool that changes them silently reconfigures every program
run afterwards. This was discovered the hard way — `focus_check.py` left white
balance locked, and the resulting red cast on the right eye looked like a
hardware fault. Every tool in this project saves the control state on open and
restores it on exit.

## 3. Depth budget and mode selection

With baseline B = 52 mm, `Z = f·B/d`. Depth error grows as Z²:
`ΔZ = Z²·Δd/(f·B)`, taking Δd = 0.25 px for SGBM subpixel matching.

| Z | 640×480 (f·B = 34.8) | 640×360 (f·B = 26.1) | 1280×720 (f·B = 52.2) |
|---|---|---|---|
| 0.5 m | ±2 mm | ±2 mm | ±1 mm |
| 1 m | ±7 mm | ±10 mm | ±5 mm |
| 2 m | ±29 mm | ±38 mm | ±19 mm |
| 3 m | ±65 mm | ±86 mm | ±43 mm |
| 4 m | ±115 mm | ±153 mm | ±77 mm |

**This is a 0.2–4 m sensor** (near limit set by §3.2, not by noise). The 52 mm baseline is short; beyond ~4 m the
depth is too noisy to be worth integrating into a map. Independent sanity check:
a ceiling in a test frame measured ~9 px disparity at 1280×720 ⇒ 5.8 m, which is
right for the room.

### 3.1 Chosen mode: 1280×480 (640×480 per eye) at 60 fps

Rationale, and this is a genuine trade-off rather than an obvious call:

- **vs 640×360**: 33% better depth precision, at the cost of 51.1° instead of
  65.0° horizontal FOV. Vertical FOV is identical (39.4°) — both modes use the
  full sensor height, so the only thing the crop costs is horizontal width.
- **vs 1280×720**: SGBM at 1280×720 runs ~3 fps on CPU, far too slow for SLAM.
- 60 fps leaves headroom; SGBM at 640×480 measures ~25 fps.

The counter-argument deserves recording: for visual odometry, a wider FOV is
often worth more than depth precision — more features, better rotation
observability, more robust loop closure. If RTAB-Map's odometry proves fragile
in Phase 8, **switching to 640×360 is a config change plus a re-calibration**,
not a redesign. See Section 12.

### 3.2 Minimum range — the binding constraint for manipulation

Target application is **in-room robot manipulation**, so the 4 m ceiling is
comfortable and the *near* limit is what matters. Two independent limits apply.

**Disparity search range — configurable.** Measured on this machine (16
threads):

| numDisparities | Min depth | Measured rate at 640×480 |
|---|---|---|
| 128 | 0.27 m | 75.9 fps |
| 192 | 0.18 m | 69.7 fps |
| 256 | 0.136 m | 60.6 fps |

All three exceed the camera's own 60 fps cap, so — contrary to an earlier
draft of this section — frame rate cannot actually be traded for near range:
even 256 disparities (60.6 fps) still keeps pace with the camera. Default
remains **192** pending the human partner's decision. `min_depth` is no
longer a hardcoded 0.18 m; it derives from the search range as
`fb/numDisparities`, so raising `numDisparities` now genuinely delivers the
near band it buys instead of having it silently discarded by a stale floor.
Depth clamped to [min_depth, 4.0] m.

**Lens focus — MEASURED, risk retired.** The lens is fixed-focus, 2.88 mm at
f/2.2, on 3.0 µm pixels, so a hyperfocal setting could have put the near limit
of acceptable sharpness as far out as 0.32–0.63 m, which would have invalidated
the whole close-range premise. It does not. Measured sweep:

| distance | L rise | R rise | corners L/R |
|---|---|---|---|
| 0.20 m | 2.56 px | 2.47 px | 21/21 |
| 0.30 m | 2.16 px | 2.21 px | 45/41 |
| 0.40 m | 1.94 px | 1.94 px | 54/48 |
| 0.50 m | 1.79 px | 1.82 px | 44/54 |
| 0.60 m | 1.73 px | 1.75 px | 54/54 |
| 0.70 m | 1.66 px | 1.73 px | 54/54 |

Three conclusions:

- **No near-focus wall.** Rise broadens only ~1.5× from best focus to 0.20 m
  — about 0.7 px of added Gaussian blur. Soft but entirely workable. **The near
  limit is therefore set by the disparity search range, not the optics.**
- **The lenses are matched** to within 1–4%, with the sign of the difference
  flipping across the range. No refocusing, no per-eye compensation. (An
  apparent 10–20% L/R asymmetry in the first, discarded VoL measurement was an
  artifact of that metric.)
- **Best focus is at ≥0.70 m**; the curve was still descending at the far end
  of the sweep.

Reduced corner counts below 0.30 m are geometric, not optical: at 0.20 m the
frame is 191×143 mm and the board is 175×250 mm, so only ~57% fits vertically.
This is the partial-view case ChArUco is chosen for. Detection is a full 54/54
from 0.55 m out, which is where calibration captures should be concentrated.

**Unmeasured:** beyond ~1.5 m a 25 mm square subtends under 8 px and the metric
declines to report, so far-field sharpness is inferred, not measured. Low risk
— a lens focused at ≥0.70 m on a 1/4" sensor at f/2.2 should carry depth of
field to infinity — but the SLAM path uses depth out to 4 m, so if far-field
softness is ever suspected, measure it on a high-contrast straight edge rather
than the board.

**Method (and why the obvious method fails).** The first attempt used
variance-of-Laplacian over a fixed centre crop and produced a non-physical
result — sharp at 0.30 m, collapsed at 0.40–0.60 m, sharp again at 1–2 m.
Defocus is unimodal, so that was the metric failing. VoL conflates blur with
target texture density in the crop, with contrast (auto-exposure was drifting),
and with motion blur. Measured directly: VoL varies 3.4× across a 3× change in
apparent board size at *identical* blur.

Phase 0 therefore measures the **10–90% edge rise width, in pixels**, across
checker boundaries on a detected ChArUco board:

- distance comes from the board's own pose via `solvePnP`, so no tape measure
  and no guessed distances;
- exposure, gain and white balance are locked for the whole sweep;
- samples are taken only when the board is holding still, so motion blur is not
  recorded as defocus;
- blur is a fixed pixel width regardless of the board's apparent size, making
  the metric scale-invariant.

Validated against synthetic blur: monotonic in σ (0.83 px at σ=0 to 8.99 px at
σ=4) and stable within 9% across a 3× change in apparent board size. Read as
~1.5–2 px = sampling-limited, >4 px = visibly soft.

Stereo overlap is *not* a limit here: with a 52 mm baseline and 51.1° HFOV, the
eyes still share 73% of the field at 0.2 m.

## 4. Architecture

```
ar0144/
  camera.py     StereoCamera  — node detection, MJPG, width assertion,
                                grab() -> (left, right, timestamp)
  board.py      ChArUco definition (single source of truth) + printable PDF
  calibrate.py  capture protocol + solve -> calibration.json
  rectify.py    Rectifier — undistort/rectify maps, rectified K, Q, baseline
  depth.py      DepthEstimator — SGBM -> disparity -> metric depth
  rgbd.py       StereoRGBD — the public API
  export.py     calibration.json -> ROS/RTAB-Map camera_info YAML
cli.py          ar0144 {board,capture,solve,view,record,export}
```

Each module is usable and testable on its own. The public surface is small:

```python
with StereoRGBD("calibration.json", mode="1280x480") as cam:
    for f in cam:
        f.rgb        # HxWx3 uint8, rectified left
        f.depth      # HxW float32, metres, NaN where invalid
        f.disparity  # HxW float32
        f.K, f.Q     # rectified intrinsics, reprojection matrix
        f.timestamp  # float, monotonic seconds
```

`camera.py` absorbs the node-detection, MJPG and fallback-guard logic already
working in `stereo_view.py`; that script becomes `ar0144 view --raw`.

### 4.1 Why alignment is free here

On an RGB-D camera like a RealSense, "align depth to colour" means reprojecting
across the extrinsic between a depth rig and a separate colour sensor. **Here
both eyes are the same colour sensor**, so depth is computed in the left
camera's own frame and RGB *is* the rectified left image. They are aligned by
construction — no warp, no resampling, no interpolation error at depth
discontinuities. This is the single biggest simplification the hardware buys us.

The output frame is therefore **rectified left**, not raw left. Un-rectifying
depth back into the raw image is possible but would add a resampling step and
its associated edge artefacts for no benefit to any consumer we have.

## 5. Calibration

### 5.1 Board

A4 portrait, printed at exactly 100%:

```
squaresX=7, squaresY=10, square=25 mm, marker=18.75 mm, DICT_4X4_50
→ 175×250 mm, 54 interior corners, 35 markers
```

Sized 7×10 rather than the 8×11 considered earlier: 8×11 at 25 mm is
200×275 mm, which leaves 5 mm side margins on A4 — inside most printers'
unprintable border, with no room for the reference block and no white quiet
zone around the edge ArUco markers. 7×10 leaves 17.5 mm side margins and 36 mm
at the foot. 54 corners is ample.

`DICT_4X4_50` covers the 35 markers needed, and 4×4 decodes more reliably than
5×5 when the board is small in frame — which it will be, given A4.

`board.py` is the single source of truth for these numbers and generates the
printable PDF, so the board that gets detected can never disagree with the board
that got printed. The page is rendered at 20 px/mm (508 dpi), which keeps every
millimetre an exact integer number of pixels.

**The page carries its own reference block**: the full parameter set
(`ChArUco 7x10 | square 25.00 mm | marker 18.75 mm | DICT_4X4_50 | 54 corners`)
and a **100 mm scale bar with 10 mm ticks**. A sheet found on a desk months
later identifies itself, and print scaling is checkable in ten seconds against
the one error that nothing downstream can detect.

Verified on generation: 54/54 corners and 35/35 markers detected from the
composed page, corner spacing 500.000 px horizontally *and* vertically against
a nominal 500 (0.000% error, aspect 1.000000), scale bar 100.25 mm, PDF page
595.276 × 841.89 pt = exact A4.

**Physical requirements, in descending order of how much damage they do:**

1. Print at 100%, no "fit to page", then **measure a square with calipers** and
   pass the measured value. Printer scaling is the most common source of a
   systematically wrong depth scale, and it is invisible downstream.
2. Mount on foam board or glass. Paper curl is unmodelled geometry; the solver
   will absorb it into the distortion coefficients and quietly degrade
   everything.
3. Matte paper, not glossy. Specular highlights destroy corner detection.

### 5.2 Capture protocol

`ar0144 capture` runs live and requires the board visible in **both** eyes
(needed for extrinsics). It:

- rejects blurry frames via variance-of-Laplacian over the board region — this
  also discovers the fixed-focus lens's near limit for free: walk closer until
  frames stop being accepted;
- tracks **FOV coverage** by binning corner positions into a grid, and **pose
  diversity** by binning board tilt, displaying both so you know when you are
  done;
- auto-captures on stability to avoid motion blur;
- targets **~50 pairs** (raised from a typical 40 to compensate for the smaller
  A4 board), weighted toward high-tilt views — tilt is what conditions the
  focal-length estimate;
- **saves raw pairs to disk**, so solving can be re-run with different settings
  without repeating the tedious part.

Work close: at 0.5 m the frame is ~0.48 m wide in the 51.1° mode, so the board
spans ~37%; closer is better up to the focus limit.

### 5.3 Solve

Per-eye `calibrateCamera` for intrinsics, then `stereoCalibrate` with
`CALIB_FIX_INTRINSIC`. Distortion model `k1,k2,p1,p2,k3` — at <0.2% lens
distortion the rational model is unnecessary and would only add variance.

**20% of pairs are held out as a validation set.** All acceptance figures below
are reported on held-out data, because reprojection error on the fitting set
measures fit, not accuracy.

### 5.4 Acceptance criteria

| Check | Threshold | What it catches |
|---|---|---|
| Per-eye RMS reprojection | < 0.3 px | bad corners, blur, bad board |
| Stereo RMS | < 0.5 px | inconsistent pair geometry |
| **Post-rectification epipolar error** | **< 0.3 px** | the thing disparity actually depends on |
| **Recovered baseline vs 52 mm** | within a few % | print-scale error, board flatness |
| Recovered f vs Table 2.1 prior | within a few % | wrong mode, crop assumption wrong |

The epipolar and baseline checks are the real gates. A calibration can show a
flattering reprojection error and still be useless for stereo.

Calibration is **per-mode**. Because the 4:3 modes crop, a calibration at
1280×720 cannot simply be rescaled to 640×480 — the crop moves the principal
point. `calibration.json` records the mode it was captured at, and loading it
against a different mode is an error, not a warning.

## 6. Rectification

`stereoRectify(..., alpha=0)`: crop to valid pixels only, so the RGBD map has no
black border. This changes the effective FOV and the intrinsics, so the
*rectified* K, the valid ROI and Q are all stored and are what the API reports.

Verification: corresponding ChArUco corners must land on the same image row to
< 0.3 px.

## 7. Depth

`cv2.StereoSGBM` on the rectified pair:

- `numDisparities=192` (§3.2), `minDisparity=0`, `blockSize` tuned (start 5),
  `P1=8·ch·bs²`, `P2=32·ch·bs²`, `mode=MODE_SGBM_3WAY`;
- left-right consistency via `disp12MaxDiff`, plus `uniquenessRatio` and
  speckle filtering;
- SGBM returns fixed-point disparity ×16; divide by 16.0;
- `depth = f·B/disparity`, invalid where disparity ≤ minDisparity or outside
  [0.18, 4.0] m.

**For SLAM, outlier rate matters more than density.** A sparse but correct depth
map produces a good map; a dense one with 5% gross outliers corrupts odometry
and drags the occupancy grid with it. Filters are tuned toward rejection, and
the recorder stores a validity mask alongside depth.

`ximgproc`'s WLS filter is not in the stock `opencv-python` wheel. If disparity
proves too sparse we add `opencv-contrib-python`; not assumed up front.

## 8. Storage format

Per frame, following the TUM/Redwood convention so Open3D and friends read it
without a converter:

- `rgb/<ts>.png` — 8-bit colour, rectified left
- `depth/<ts>.png` — **16-bit PNG, millimetres, 0 = invalid** (caps at 65.5 m)
- `meta.json` — rectified K, Q, baseline, mode, per-frame timestamps

## 9. RTAB-Map integration

RTAB-Map accepts this camera by two routes. Both need the same calibration
export, which is why `export.py` exists.

### 9.1 Calibration export

`ar0144 export` writes `<name>_left.yaml` and `<name>_right.yaml` in the ROS
`camera_info` format that both RTAB-Map standalone and `rtabmap_ros` read:
`camera_matrix`, `distortion_coefficients` (`plumb_bob`), `rectification_matrix`
(R1/R2), `projection_matrix` (P1/P2).

Two traps, both worth automating rather than remembering:

- **`image_width` must be the per-eye width (640), not the 1280 the driver
  advertises.** This is the single most common side-by-side stereo
  misconfiguration.
- **`P2[0,3] = -fx·B`**, negative. OpenCV's `stereoRectify` already returns P2
  in this convention, so it is a direct copy — but the sign is worth asserting
  in a test, because getting it wrong yields a mirrored, plausible-looking map.

### 9.2 Route A — RTAB-Map standalone (recommended first)

RTAB-Map's **"Video Side-by-Side"** stereo driver consumes exactly this
camera's native format: one video device, left|right in one frame. Point it at
the device, load the exported YAMLs, and no code of ours sits in the loop.

This is the fastest path to a map and the best way to find out whether the
52 mm baseline is adequate for the target environment before investing in
integration.

### 9.3 Route B — feed our pipeline's output

If a custom loop is needed, give RTAB-Map **rectified stereo**, not precomputed
RGBD, for odometry.

**Mechanism.** RTAB-Map never builds a dense map for odometry. It takes the
features already extracted in the left image and finds each correspondence in
the right image directly — iterative Lucas-Kanade when `Stereo/OpticalFlow=true`,
otherwise SSD block matching in a `Stereo/WinWidth=15` × `Stereo/WinHeight=3`
window (wide and thin, because on a rectified pair the search runs along the
epipolar row). One disparity per feature, computed exactly where it is needed.

Routing through our RGBD inserts three lossy steps that the direct path skips:
SGBM quantises disparity to 1/16 px, applies a global smoothness prior, and then
we sample that map at the feature location. Features are corners and object
silhouettes — **depth discontinuities** — which is precisely where SGM path
aggregation is weakest (foreground fattening, streaking) and where a matching
window straddles two surfaces.

**No robustness is lost.** Both routes are passive stereo on the same rectified
pair; where our SGBM fails on a textureless wall, RTAB-Map's feature matcher had
no features there either. Against a RealSense this argument would fail — its IR
projector paints texture the RGB features cannot see — but this module has no
projector, so a dense map buys no coverage the feature path lacks.

This is a design argument, not a benchmark on this camera in this room. Phase 8
measures trajectory drift both ways; both paths exist, so the comparison is
nearly free.

### 9.3.1 Two consumers, two requirements

The dense pipeline is not redundant — it simply serves a different consumer:

| Consumer | Needs | Path |
|---|---|---|
| RTAB-Map VO/SLAM | sparse, accurate, fast | rectified stereo → RTAB-Map's own correspondence |
| Manipulation perception (grasping, collision, workspace clouds) | dense, metric, aligned | our SGBM → RGBD |

Same calibration, same rectification, two outputs. Rectified stereo is already
an intermediate product of Section 6, so supporting both costs almost nothing.
Because the dense path is perception rather than odometry, it is not bound to
60 fps, which is what lets §3.2 spend frame rate on near range.

### 9.4 Parameters implied by Section 3

`Vis/MinDepth ≈ 0.2`, `Vis/MaxDepth ≈ 4.0`. Leaving MaxDepth unbounded lets
far, noisy points dominate and is the most likely cause of drift with this
camera.

Global shutter and hardware sync are the two properties that make this module a
reasonable SLAM sensor at all: no rolling-shutter skew during motion, and no
inter-eye time offset to corrupt triangulation.

## 10. Testing

| Level | Test | Passes when |
|---|---|---|
| Unit | Board generate → detect round trip | all 54 corners found in the composed page |
| Unit | Synthetic depth: known K, B, constant disparity | `depth == f·B/d` exactly |
| Unit | Depth ↔ disparity round trip | within float tolerance |
| Unit | `P2[0,3]` sign and per-eye width in exported YAML | matches Section 9.1 |
| Integration | Camera guard | single-width node is rejected, not split |
| Integration | Calibration on held-out pairs | Section 5.4 thresholds |
| Integration | Rectification row alignment | corners same row < 0.3 px |
| Integration | Save → reload RGBD | depth values identical |
| **End-to-end** | **Flat wall at tape-measured 0.5/1/2/3 m** | **mean depth within the Section 3 error budget; plane-fit RMS reported** |

The wall test is the only one that validates the whole chain. A print-scale
error in Section 5.1 survives every other test and shows up here as a
consistent percentage bias — which is also how we would diagnose it.

## 11. Known limitations

- **Timestamps.** OpenCV's `VideoCapture` does not expose V4L2 kernel buffer
  timestamps, so frame time is taken with `time.monotonic()` immediately after
  `read()` returns and carries USB transfer and MJPEG decode latency (a few ms,
  with jitter). Acceptable at 30–60 fps for RTAB-Map. If it limits odometry
  quality, the fix is a direct V4L2 capture path reading
  `struct v4l2_buffer.timestamp`.
- **Depth beyond 4 m is not usable** for mapping. Section 3.
- **OpenCV 5.0.0** is recent; all required calib3d functions are present
  (`calibrateCamera`, `stereoCalibrate`, `stereoRectify`,
  `initUndistortRectifyMap`, `reprojectImageTo3D`, ChArUco in the stock wheel),
  but a signature may differ from the 4.x examples in circulation.
- No CUDA in the pip OpenCV build; SGBM is CPU. An RTX 4070 Laptop is present
  and unused.

## 12. Deferred, with triggers

| Deferred | Pull it in when |
|---|---|
| ROS 2 node | **Dropped, not deferred** — user confirmed no ROS 2 |
| 640×360 wide-FOV mode | odometry is fragile for lack of field of view (§3.1) |
| Learned stereo (RAFT-Stereo etc., 4070 available) | SGBM depth quality is the limiting factor *after* calibration is verified clean |
| `opencv-contrib` WLS disparity filter | disparity is too sparse for the occupancy grid |
| Direct V4L2 timestamps | timestamp jitter limits odometry (§11) |
| Per-eye RMS reported on held-out pairs (§5.3 says all figures should be; only epipolar currently is) | a calibration passes the gates but the wall test shows bias |
| Normalising over the stereo overlap region rather than the full frame (§2.3) | disparity quality is poor at the near limit, where non-shared columns are ~30% of the frame |
| Persisting raw capture images so a wrong `--square-mm` can be corrected by re-solving (§5.2) | a print-scale error is discovered after a capture session |
| Per-eye colour gains measured and stored at calibration (§2.3 items 2-3) | the debug RGBD output's colour fidelity matters, or a colour-dependent consumer appears |

The ordering matters: **do not reach for a better matcher before the
calibration passes Section 5.4.** Bad extrinsics look exactly like a bad
matcher, and swapping the matcher is the more satisfying thing to do, which is
why it is the more common mistake.

## 13. Implementation phases

Each phase has a verification step; no phase closes until it passes.

0. ~~**Focus / near-limit measurement**~~ (§3.2) — **DONE**. No near-focus
   wall; lenses matched to 1–4%; near limit set by the disparity search, not
